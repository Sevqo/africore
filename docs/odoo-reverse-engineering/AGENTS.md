# Odoo source-driven implementation notes

Start with README.md, odoo20-community-index.json and feature-map.json. The static
reports and dependency graph are generated by scripts/odoo-reverse-engineering-index.py.
The implementation ledger and feature map are maintained per checkpoint.

From the AfriCore repository root, run
`python scripts/odoo-reverse-engineering-index.py --odoo-root ../odoo-reference --output-dir docs/odoo-reverse-engineering`.
Add --reuse for the same source commit and index schema. Omit it after changing
the extraction rules. A new source commit triggers a fresh inventory.

- Record the Odoo SHA and AfriCore baseline for each feature.
- Odoo is a separate read-only checkout; never add it to app builds, packages,
  Git, or deployment artifacts.
- Use REA only where the installed operation supports the target. REA 6.10.1
  cannot import this Python source tree from Windows; do not claim it indexed it.
- Inspect the selected feature's dependency closure, models, security, views,
  actions, controllers, tests and hooks before choosing reuse/adaptation.
- AfriCore owns identity, tenant boundaries, entitlements, audit, exact-money
  ledger, source records and approvals. Python adapters cannot become another
  authority.
- Record source provenance, license obligations, unsupported behavior and
  verification status. A helper or endpoint does not establish app parity.
- Keep checkpoints bounded, locally tested and uncommitted. No hosted SQL,
  production secrets, deployments or pushes without a separate request.
