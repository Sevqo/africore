## Architecture comparison

Odoo Community composes applications from addon manifests and a shared ORM. `odoo/addons/base/models/ir_model.py`, `ir_ui_view.py`, `ir_actions.py`, and `ir_ui_menu.py` provide model metadata, access, views, actions and menus; `addons/web` supplies the common web client and view implementations. Addons add models, inherited views, menu/actions, access CSV/rules, controllers, data and tests. The business record is normally shared in the same database/transaction across installed addons.

AfriCore composes installed application workspaces from `src/apps/catalog.ts`, with service definitions and activation/entitlement behavior in `src/marketplace/catalog.ts` and `src/marketplace/engine.ts`. The UI dispatch is in `website/src/apps/AppsWorkspace.tsx`; direct service access remains in `website/src/BusinessApp.tsx`. Authoritative APIs and business rules live in service areas such as `src/erp`, `src/operations`, `src/inventory`, `src/finance`, `src/commerce`, `src/pos`, and `src/trust`. Workspace/environment/current-role access is rechecked by the server; a visible UI control is not authorization. Cross-app operations therefore need explicit service/API handoffs rather than shared in-process ORM writes.

This separation is intentional. Preserve canonical customers, products, orders, invoices, stock, People records, documents and trust evidence; do not add application-owned copies. Before extending any app, reconcile its required/optional services in `src/apps/catalog.ts` with actual selectors and backend prerequisites, then inspect route schemas and service permissions. The existing report documents service dependencies in `docs/PHASE2_APP_PROGRESS.md` and service definitions in `docs/SERVICE_CATALOG.md`.

## Recommended implementation sequence

This is a dependency-aware sequence proposal, not authorization to resume coding.

1. **Close active 2.10 People acceptance**: preserve the current uncommitted code; run founder role/browser checks for employee privacy, compensation, leave, reviewer, attendance, document link and policy failure states. Fix only found issues. No payroll scope unless separately specified.
2. **Resolve service/app prerequisites and all-or-nothing reads**: POS Customers registry mismatch first; then Finance, Analytics, Automation, CRM and Documents independent-source failures. Add focused UI-level recovery tests if the current test stack supports them.
3. **Reconcile canonical transaction flows**: Sales → Inventory/Fulfillment → Invoicing → Accounting; Procurement → accepted receipts → Inventory and bill → Accounting; POS/Commerce → Orders/Invoicing/Payment evidence. Exercise invalid config, role, stale version, duplicate intent and pagination for each.
4. **Finish app-specific missing capability in dependency order**: Finance overview (without ledger duplication); CRM report/notification/merge limits; Procurement vendor/receipt model decision; Inventory partial/lot/valuation decisions; POS device/provider qualification; Commerce publish/checkout gates. Add functionality only after authoritative services exist.
5. **Complete Documents checkpoint**: it is the next phase app (2.11), but Community has no `documents` module. Base attachment is reference only. Verify secure custody, roles, versions and links with People/Work/Sales and decide scan/retention requirements before release.
6. **Build Analytics on complete APIs**: source-specific coverage, server aggregates, saved definitions, drill-down and currency semantics before adding spreadsheet-like authoring.
7. **Extend Automations last among operational apps**: only after stable source events, workers, idempotent actions, current authorization, audit, retry and dead-letter controls are established.
8. **Treat Business ID as a distinct AfriCore domain**: define assurance/issuer/consent governance and manual acceptance; Odoo has no equivalent module to copy.
